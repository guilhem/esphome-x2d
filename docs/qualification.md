# ESP32-S3 qualification

No ESP32-S3/CC1101 waveform or motor qualification has been performed for this implementation. The normal example and CI builds keep RF disabled. Host simulation, code generation and compilation are separate evidence.

## Private trial authorization

Retain the existing supervised Well'com hypothesis: a fresh random nonzero 16-bit prefix plus the privately observed identity suffix, initial counter zero, 24 copies per enrollment phase, and a 2001 ms start-to-start separation. Commands use 25 copies. None of these parameters establishes general motor compatibility.

Create an ignored `*.private.yaml` configuration derived from the example. Set both `transmit_enabled` and `enrollment_enabled` to `true`. In `esphome.build_flags`, supply all three definitions explicitly:

- `-DX2D_TRIAL_SLOT=N`, where N is 1…16.
- `-DX2D_TRIAL_IDENTITY_SUFFIX=VALUE`, with your privately verified byte value. There is no default.
- `-DX2D_TRIAL_EXPECTED_NEXT_COUNTER=0` for a fresh attempt, or `2` for a deliberate retry using the existing pending identity.

Do not publish this configuration or its binaries. The component rejects a missing/out-of-range authorization at compile time. The first free or existing pending slot must equal N. A counter mismatch refuses the request before RF. An authorization for counter 2 cannot create a new identity. There are no automatic retries, counter resets, arbitrary seeds or fallback suffixes. Confirmation is authorized only for the same pending slot after at least two counters were reserved, and always means the human observed the motor response.

To test another slot, first finish confirming the previous slot and explicitly update the private trial authorization. The software supports 16 inventory slots; this per-slot lab gate remains until the identity/association profile has physical evidence. A commands-only build uses `transmit_enabled: true` and `enrollment_enabled: false` with already confirmed identities, keeping association disabled.

## Required measurements

Record board/module/motor models, firmware and core SHAs, wiring, supply, clock calibration, capture equipment and the raw captures. Use only disposable test motors and supervised movements.

1. **Boot and faults:** capture GDO0 and RF during power-up, reset, brownout and watchdog while transmitting. Verify the external pull-down suppresses the carrier and measure the maximum time to carrier-off. Verify boot issues CC1101 reset/IDLE and never emits a command.
2. **Waveform:** compare RMT captures against core-generated chips and an observed remote/known transmitter. Check polarity, chip duration, one preamble, copy continuity and phase, footer and full final chip, including odd run counts. Verify repeated idle-to-transmit transitions preserve the GPIO matrix route and produce a waveform on GDO0. Recheck after chip calibration.
3. **Interrupt latency:** exercise Wi-Fi/API traffic, logging and NVS writes during a burst. Inject ISR stalls shorter and longer than a half-buffer. The refill monitor has a 1 ms margin, a 1 ms early/5 ms late completion tolerance and a 50 ms completion watchdog; these software thresholds need bench validation. Every injected missed deadline must return `unknown` and latch RF off. Detection cannot undo emitted stale symbols.
4. **STOP:** issue STOP at different offsets under load. Capture accepted STOP to the previous burst's last chip, then to the STOP burst's first chip. Record p99 and maximum latency and verify each normal truncation ends at a full, not-yet-prefetched frame. Do not advertise the RP2040's one-frame latency or treat network button latency as a hardware bound.
5. **Association:** use new private identities, verify the initial 0/1 attempt and only deliberately test 2/3 retry. Confirm the motor's actual response before pressing Confirm. Power-cut before/after both reservations and between phases. Verify no counter reuse, no restart/reconnect emission, and confirmation after reboot without retransmission.
6. **Movement and malformed transmissions:** verify open, close and STOP on the target motor. On a sacrificial motor, capture the behavior of truncated or half-repeated frames generated by injected faults. Unexpected actuation blocks qualification.
7. **Home Assistant and OTA:** confirm stable entity IDs and custom names through another association/reboot. Check pending and unused slots remain absent. Interrupt application OTA while RF is active and while idle: first flash write must follow radio quiescence, counters remain consumed, failed OTA never replays work. Verify the journal partition bytes and inventory survive a successful app update.

Do not enable normal association or announce compatibility when any gate fails. Record the failed criterion and keep the supervised authorization. Widening the identity/counter policy requires new motor evidence, not a successful host test.
